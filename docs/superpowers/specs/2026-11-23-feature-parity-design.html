Anki MCP parity plan

Parity with eight other Anki servers, then the two things your own Anki skills need that none of them has: flags, and scheduling transfer with every write checked.

Outcome

Each Anki step in your skills is one tool call, and the known AnkiConnect traps are handled by the server.

Done means

  • Tests pass, including a regression test per bug found
  • No write can no-op silently and still report success
  • You confirm flags and scheduling once in real Anki

Approach

Tools at the level of what you want done, each checking its own writes. No raw passthroughs, and none of your pipeline's tag conventions.

Stages

  1. Parity tools
  2. Adding a batch of cards
  3. Setting a flag
  4. Seeing and finding flags
  5. Copying scheduling onto a redesigned card

Adding a batch of cards

Exists

One bad card in a batch must not sink the rest, or hide the IDs of the cards that were saved.

turn each card into an Anki note (MathJax and code converted as add_note does)
send every note in one request, each as its own addNote action
for each note
  if Anki saved it
    report added, with its note ID
  else
    report failed, with Anki's reason (for example a duplicate)

Your partApprove the cards as you do now. Nothing changes in your approval step.

GuardEach note succeeds or fails alone, so the report always matches what is in Anki.

Setting a flag

To build

Your pipeline runs on flags (red = bad card, green = good, orange = maybe beyond FY1), but no tool sets them.

take card IDs and a colour name
in one request, write the flag number onto each card
read the cards back
for each card
  if the flag now matches
    report set
  else
    report unchanged, with the flag Anki holds

Your partNothing. Colour names follow Anki's own numbering.

GuardThe read-back catches the silent no-op that your skill warns about for setSpecificValueOfCard.

Copying scheduling onto a redesigned card

To build

A redesigned card should keep the original's progress, as your sched_transfer.py does, without the silent-failure trap.

take the target cards, and one source card or note
if the source is a note
  use its card with the longest interval
if the source has never been reviewed
  stop: there is nothing to copy
if any target already has reviews, and overwrite_history is not set
  stop: protect real progress from a wrong ID
set the targets due across the next week (0-6 days)
write the source's interval and ease onto each target, as whole numbers
read the targets back
for each target
  if interval and ease match
    report copied
  else
    report mismatch, with expected and actual

Your partCheck the two calls I made: the history guard, and the 0-6 day spread (your pipeline's spread).

GuardNo rollback after a partial failure: the report names exactly which cards to redo, and a rollback would be one more write that can fail.
